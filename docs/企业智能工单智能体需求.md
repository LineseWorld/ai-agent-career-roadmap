# 主项目需求：企业智能工单 Agent

## 1. 项目定位

### 项目名称

Service Desk Copilot——企业智能工单与故障排查 Agent。

### 业务背景

某软件公司的客户通过聊天窗口提交问题，例如登录失败、消息发送失败、会议无法加入、接口超时和数据库异常。客服需要查询客户信息、产品文档、历史工单和服务状态，再决定直接回复、执行诊断工具或创建工单。

公司希望建设一个 Agent，在受控范围内完成：

- 理解用户问题；
- 查询知识库；
- 查询客户和服务状态；
- 执行只读诊断；
- 创建、分派和更新工单；
- 高风险操作转人工确认；
- 保存完整处理轨迹；
- 对处理效果进行评测。

该项目完全使用软件模拟，不依赖STM32、串口或Modbus设备。

## 2. 为什么适合当前背景

- IM经验可用于多轮对话、消息状态和会话持久化；
- 会议控制经验可用于状态机、权限和流程编排；
- HTTP经验可用于Agent工具和第三方系统集成；
- 数据库经验可用于客户、工单、知识库和审计；
- C++ SDK经验可体现接口设计、错误处理和工程质量；
- Linux经验可用于Docker部署、日志和故障排查。

## 3. 最终演示场景

用户输入：

> 我们公司的用户从今天上午开始无法加入会议，提示错误码 M-102。请帮我排查，如果确认是服务异常就创建一个高优先级工单。

Agent执行：

```text
识别客户与问题
→ 查询客户权限和产品版本
→ 查询 M-102 知识库
→ 查询服务健康状态
→ 查询相似历史工单
→ 生成诊断结论
→ 请求确认创建高优先级工单
→ 创建并分派工单
→ 返回工单号、依据和后续建议
```

## 5. 领域模型

### Customer

| 字段 | 说明 |
|---|---|
| id | 客户唯一标识 |
| name | 客户名称 |
| plan | FREE、STANDARD、ENTERPRISE |
| status | ACTIVE、SUSPENDED |
| products | 已购买产品列表 |

### Conversation

| 字段 | 说明 |
|---|---|
| id | 会话ID |
| customer_id | 所属客户 |
| status | OPEN、WAITING_USER、RESOLVED、ESCALATED |
| summary | 会话摘要 |
| created_at | 创建时间 |

### Ticket

| 字段 | 说明 |
|---|---|
| id | 工单ID |
| title | 标题 |
| description | 问题描述 |
| customer_id | 所属客户 |
| priority | LOW、MEDIUM、HIGH、URGENT |
| status | OPEN、IN_PROGRESS、WAITING、RESOLVED、CLOSED |
| assignee | 处理人或团队 |
| source | MANUAL、AGENT |

### ToolExecution

记录Agent调用的工具、参数、结果、耗时、错误和关联会话。

## 6. 阶段一：Python后端MVP

本阶段不接入LLM。

### REQ-001 客户管理

实现：

```http
POST /api/v1/customers
GET  /api/v1/customers/{customer_id}
GET  /api/v1/customers?status=ACTIVE&limit=20&offset=0
```

验收条件：

- ID唯一，重复创建返回409；
- 枚举和分页参数经过校验；
- 不存在时返回404及稳定错误码；
- 第一轮可使用内存Repository。

### REQ-002 工单创建与查询

实现：

```http
POST /api/v1/tickets
GET  /api/v1/tickets/{ticket_id}
GET  /api/v1/tickets?customer_id=xxx&status=OPEN
```

验收条件：

- 客户必须存在且状态为ACTIVE；
- title长度为5～100；
- description不得为空；
- 创建后状态默认为OPEN；
- 支持按客户、状态和优先级过滤。

### REQ-003 工单状态机

合法转换：

```text
OPEN → IN_PROGRESS
IN_PROGRESS → WAITING
WAITING → IN_PROGRESS
IN_PROGRESS → RESOLVED
RESOLVED → CLOSED
RESOLVED → IN_PROGRESS（重新打开）
```

非法转换返回 `INVALID_TICKET_TRANSITION`，每条规则必须有测试。

### REQ-004 会话和消息

实现会话创建、追加消息、查询消息历史和关闭会话。消息需要包含角色、内容和时间。

验收条件：

- 已关闭会话不能继续追加消息；
- 消息按时间稳定排序；
- 支持分页；
- 空消息被拒绝。

## 7. 阶段二：异步与外部系统模拟

### REQ-101 服务健康Mock API

创建独立Mock服务：

```http
GET /mock/status/{service_name}
```

支持模拟：正常、性能下降、故障、超时和500错误。

### REQ-102 并发诊断

诊断接口需要并发查询：

- 账户状态；
- 产品权限；
- 服务健康；
- 最近工单。

验收条件：

- 单项超时不阻塞其他查询；
- 最多并发5项；
- 返回部分成功结果；
- 每项结果包含耗时和错误码。

### REQ-103 重试与熔断

- 网络临时错误最多重试2次；
- 4xx业务错误不得重试；
- 连续失败触发短时间熔断；
- 日志记录每次尝试；
- 测试正常、重试成功、重试耗尽和熔断场景。

### REQ-104 幂等创建工单

通过 `Idempotency-Key` 防止Agent重复创建相同工单。相同键但内容不同时返回409。

## 8. 阶段三：原生Tool Calling Agent

### REQ-201 Agent任务接口

```http
POST /api/v1/agent/tasks
```

输入自然语言问题，返回task_id；客户端可以查询状态或通过SSE接收进度。

### REQ-202 Agent工具

实现：

- `get_customer`
- `get_service_status`
- `search_recent_tickets`
- `search_knowledge`
- `create_ticket`
- `update_ticket`
- `request_human_help`

约束：

- LLM只能选择已注册工具；
- 参数经过Pydantic校验；
- 工具必须调用现有Service层；
- 一次任务最多8步；
- 所有调用保存ToolExecution记录。

### REQ-203 人工确认

以下操作必须确认：

- 创建URGENT工单；
- 修改或关闭已有工单；
- 向客户发送最终处理结论；
- 执行任何未来增加的写操作。

等待确认时任务状态为WAITING_APPROVAL，服务重启后仍能恢复。

## 9. 阶段四：LangGraph工作流

工作流节点：

```text
classify_request
load_customer_context
search_knowledge
run_diagnostics
create_resolution_plan
validate_plan
wait_for_approval
execute_action
verify_result
generate_response
```

验收条件：

- 节点状态可持久化；
- 失败可以定位到具体节点；
- 已完成写操作不会因恢复而重复执行；
- 不确定时升级人工，不编造结果。

## 10. 阶段五：知识库RAG

知识库内容：

- 产品使用手册；
- 错误码说明；
- 常见问题；
- 故障处理流程；
- 脱敏历史工单。

功能要求：

- 上传PDF、Markdown和TXT；
- 文档分块、Embedding和pgvector入库；
- 关键词与向量混合检索；
- 支持产品、版本和文档类型过滤；
- 回答显示来源；
- 无依据时拒答；
- 文档中的指令不能触发工具。

## 11. 阶段六：评测与可观测性

建立至少40条案例，覆盖：

- 单纯知识问答；
- 需要查询API的问题；
- 需要组合多个工具的问题；
- 应创建工单的问题；
- 必须转人工的问题；
- 信息不足的问题；
- Prompt注入和越权请求。

统计：

- 意图分类正确率；
- 工具选择正确率；
- 工具参数正确率；
- 工单创建正确率；
- 越权操作拦截率；
- RAG检索与引用正确率；
- 端到端任务成功率；
- 平均延迟和Token成本。
